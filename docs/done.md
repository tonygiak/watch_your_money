## Sprint S-011 — Auth modernization + JWT header logging contract (closed 2026-05-12)

> Implementation sprint. **Three BLGs shipped together in one PR** per the ADR-0015 §8 + ADR-0016 §3 hard-ordering constraint: BLG-0023 (asymmetric JWT verifier), BLG-0024 (mobile soft auth-error), BLG-0025 (JWT-header-logging contract + tests). The 2026-05-12 incident class — "Supabase auto-rotates signing keys, every backend endpoint returns 401" — is now structurally impossible at the verifier level, and a transient JWKS-unreachable window no longer signs the user out. `make check` posture: **389 tests across 21+ suites — green** (346 → 389 = +43: 39 new backend tests covering ES256 / RS256 / HS256-transitional / JWKS-cache / header-extraction + the redaction-regex scan, plus 4 new mobile tests covering the recoverable / terminal auth-error split). - **BLG-0023 — Asymmetric Supabase JWT verification** *(M, security)*. `backend/app/auth.py` rewritten end-to-end per ADR-0015. New runtime dep `cryptography==45.0.1` in `backend/requirements.txt` (one dep, not two — PyJWT was rejected in ADR-0015 Round 1 on supply-chain grounds; PyCA-maintained, OpenSSF-backed, exact pin so Railway / Render builders never pick up a surprise upgrade on the auth-critical path). Algorithm allowlist `{ES256, RS256, HS256-transitional}` with the full ADR-0015 §4 cross-check matrix: `alg=none` rejected, unknown `alg` rejected, alg/key-type mismatch rejected, `alg=HS256` with an asymmetric `kid` rejected, missing-`kid` on asymmetric alg rejected, JWKS-unreachable hard-fails with `JwtMalformedError("jwks_unreachable")` (never silently accepts unverified tokens). New `CachedJwksProvider` (600 s TTL, 60 s refetch-floor — global state across requests per ADR-0015 Round 2; serves stale keys on a failed refetch when the cache already has material rather than rejecting every request); injectable `JWKSProvider` Protocol so tests never hit the network (production wires the Supabase JWKS endpoint, tests inject `InMemoryJwksProvider`). Config evolution: `SUPABASE_JWKS_URL` (defaults to `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`), `SUPABASE_JWKS_CACHE_TTL_SECONDS` (default 600), `SUPABASE_JWT_LEGACY_HS256_SECRET` (transitional), `SUPABASE_JWT_SECRET` honored as a deprecated one-cycle alias with **boot-time fail-loud if both are set to different values** per ADR-0015 §5 Round-2 (`backend/app/config.py:_resolve_legacy_hs256_secret`). The `JwtError` taxonomy is preserved verbatim from ADR-0002 §4 / ADR-0015 §6 so every route's RFC-7807 mapping (`unauthenticated` envelope; never echo the specific reason in `type`) is byte-identical. The DI surface in each of the five protected routes (`backend/app/routes/{receipts,receipt_tag,insights,users,exports}.py`) gains a `get_jwks_provider` hook alongside the existing `get_jwt_secret` (kept as the symbol name for test backwards-compat: `get_jwt_secret` now returns the legacy HS256 secret; tests' `app.dependency_overrides[get_jwt_secret] = lambda: JWT_SECRET` continue to work). Production `JWKSProvider` factory in `backend/app/services/jwks_provider.py` is a lazy module-level singleton, reset-able for tests. `cryptography==45.0.1` co-signed by `agent-safety-officer` + `engineering-manager` in ADR-0015 Round 1.

- **BLG-0024 — Soft auth-error handling on the scanner** *(S, product)*. `mobile/src/screens/scanner/state.ts` reducer extended with two new states (`auth_error_recoverable`, `auth_error_terminal` — replacing the old single `auth_error`) and a new action `RETRY_AFTER_REFRESH`. State carries a `hasAttemptedAuthRefresh` flag: the first 401 routes to recoverable; on `RETRY_AFTER_REFRESH` the flag is bumped and the state goes back to `submitting`; a *second* 401 with the flag set routes to terminal. Success on the retry resets the flag for the next scan. `mobile/App.tsx#refreshSession` is the new adapter — silently calls `supabase.auth.refreshSession()`, updates the session on success, returns a boolean; the scanner consumes it through props (no screen imports `@supabase/supabase-js` for refresh — ADR-0015 §8). On `auth_error_recoverable` the camera surface shows an in-context overlay with the new `scanner.error.auth.refreshing` string (el: "Επαναφορά σύνδεσης…", en: "Refreshing session…") while the refresh round-trip is in flight; no user action is required and no sign-out flashes. Tag / profile / receipt-detail screens still use the legacy `onAuthError` callback today (logged as a follow-up: `Scanner is the live-incident-hit surface; tag/profile/receipt-detail parity will land alongside the next non-trivial change there.`). Pure-TS reducer tests (`mobile/__tests__/screens/scanner/state.test.ts`) cover all five new branches per BLG-0024 acceptance: first-401 → recoverable, RETRY_AFTER_REFRESH → submitting + flag bumped, RETRY_AFTER_REFRESH no-op outside recoverable, second-401 → terminal, success after refresh resets the flag. Telemetry adds `submit_auth_refresh_attempt` for the recoverable transition (counts only — no token / phone / payload ever logged per `agent-runtime-security.md` §3 + ADR-0004 §5 + ADR-0016).

- **BLG-0025 — JWT-rejection diagnostic log line formalized + ADR-0002 §6 amended** *(XS, engineering)*. Header-extraction logic moved from the inline block in `backend/app/routes/receipts.py` (the in-session 2026-05-12 patch) to `app/auth.py:extract_header_metadata(token) -> HeaderMetadata` per ADR-0016 §2 backend-builder Round 1. The `jwt_exception_handler` log line is unchanged in shape — `code` + `alg` + `typ` + `kid` (truncated to first-6-chars + "…" when > 6 chars) + static `reason` — but is now exhaustively tested by `backend/tests/test_auth_logging.py` (9 tests, ≥ 8 per ADR-0016 §3): per-subclass emission (`JwtMalformedError`, `JwtSignatureError`, `JwtExpiredError`, `JwtClaimError` all surface their static `code=...`), `alg`/`typ`/`kid` correctness from a real header, kid truncation rule (long → `first6…`; ≤6 → as-is), malformed-token tokens log `alg=None typ=None kid=None` and do NOT crash, missing-`Authorization`-header path also logs `None` fields, **the redaction regex scan** finds zero JWT-shaped strings + zero `Bearer <token>` substrings + zero literal payload claims (`email`, `phone`) across every captured log record in the suite (defense-in-depth: this test alone would catch a future careless logging line *anywhere* in the codebase that ever leaks a token), and a final sanity check that the redaction regex itself recognizes a real JWT (so the negative-contract assertion is not a false negative). Static-`reason` discipline enforced — `JwtClaimError("unexpected aud")` no longer f-string-interpolates the claim value, so payload data cannot leak via the `reason` field even when the offending value is user-supplied (ADR-0016 §1 / Round-1 `security-privacy-officer`).
